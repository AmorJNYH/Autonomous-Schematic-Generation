## 4. 步骤–任务分解

### 4.1 对照实际设计流程

工程上一块板的原理图通常走：需求分析 → 方案设计（系统框图、电源树、核心器件预选，方案评审）→ 详细设计
（按数据手册设计外围电路、参数与应力计算、连接关系）→ 原理图绘制 → 设计检查（ERC、网表比对、自查）→ 设计输出
（BOM、网表、PDF、设计文档）→ 独立的设计评审。ASG 现在的划分有四处与此不符：

| 现在 | 问题 | 调整 |
|---|---|---|
| 分页放在第 1 步“架构与分页” | 分页是绘图决定；架构阶段定的是功能块、能量与信号流向、隔离与接口 | 分页移到原理图绘制 |
| 选型放在第 2 步，与计算同一步 | 核心器件和拓扑一起决定方案；ASG 已规定选型方案须用户定下才进入设计网表，这正是方案评审的位置 | 选型移到需求与方案，作为方案确认 |
| 组装根图放在第 6 步“组装与一键验证” | 组装是绘图的收尾，检查的对象是组装结果 | 组装移到原理图绘制 |
| “继续可完成的设计项”放在第 8 步交付 | 它是交付前的设计完成核对，不是交付动作 | 作为设计输出的第一项任务，标明是核对 |

独立审查（SR）在设计输出之后，按 P6 不属于 ASG。

### 4.2 划分

五个步骤、15 项任务，每步不超过 5 项。每个任务写：做什么、产出、**做完的标志**（取自脚本已有的输出，不新造判断）。
SKILL.md 的“架构”一节加一张步骤–任务总表（同 SR）；原各步的规则文字搬到对应任务下，不删内容。

| 步骤 | 任务（来自原步骤） | 产出 | 做完的标志 |
|---|---|---|---|
| **① 需求与方案** | 1.1 需求追溯（原 0） | `design-closure.json` 的 `requirements`；架构级待定项的用户答复 | 每条需求有功能路径与承担器件或 `[]` 加理由；会改变架构的待定项已一次问清（`user:<日期>`），其余记 `requirement` 待办 |
| | 1.2 系统架构（原 1 的框图部分） | 功能块、能量与信号流向、隔离边界与接口（System_block 的内容） | 每个功能块有输入输出和所在电压域；跨隔离的信号都有名字 |
| | 1.3 功能块做法（原 1 的模式查找） | 每块对应的电路模式与做法 | 每块有 `find_parts.py --patterns` 找到的做法，或在 `lessons.json` 登记 `knowledge_missing` |
| | 1.4 核心器件选型与方案确认（原 2 的选型） | `selection.json`；依赖未公开资料的角色的方案、建议与用户决定 | 报告的选型检查无问题；有外部依赖的角色都有 `decision`（`user:<日期>`） |
| **② 详细设计** | 2.1 数据手册核对与外围电路（原 2 的手册核对、资料入库） | `reference-input.json`、外围电路要求、入库的手册 | 外围电路核对表检查项通过或列出资料不足项；分立器件符号含义与料号一致；入库检查通过 |
| | 2.2 设计计算（原 2 的计算） | `design-closure.json` 的 `calculations`（工况角点、单点故障、热） | 审计无错误，没有 `failed`，结论由参数依据推出 |
| | 2.3 设计网表（原 3） | `electrical-intent.json`、外部供电声明、`design-preflight.json` | 每个物理引脚接网络或有依据地标 NC；`net_roles` 覆盖电源轨与阈值/反馈网络；生成前预检 PASS 或 CONDITIONAL |
| **③ 原理图绘制** | 3.1 分页方案（原 1 的分页、原 4） | `page-plan.json` | 报告的分页方案检查无问题：每个器件属于一个功能块，每块标注模式；小块已合页 |
| | 3.2 图页脚本（原 5） | `record/scripts/` 下的图页脚本 | `Sheet.build()` 不报错（结构审计与可读性 PASS，无四线交汇、无位号块互换）；每页间距豁免不超过 3 处 |
| | 3.3 组装工程（原 6 的组装） | 根图 System_block、各页、`.kicad_pro`、`sym-lib-table` | `Root.write()` 不报错（流向线有名字、隔离边界不穿页块） |
| **④ 设计检查** | 4.1 自动检查（原 6 的验证） | `summary.json`、ERC、导出网表、PDF | 无 FAIL，资料不足项逐条列出；失败靠改图关闭，不靠 PWR_FLAG、豁免或改引脚类型 |
| | 4.2 图面审阅（原 7） | `visual-review.json` | 每页路径数不少于读者任务数；每个图面待审对象写出在本版 PDF 上看到了什么；`REVIEWED` 时 `pdf_sha256` 对得上本版 PDF |
| **⑤ 设计输出** | 5.1 设计完成核对（原 8 的“继续设计”） | 更新的记录 | 待办只剩外部依赖、技术转交与已登记的设计待办；还能独立完成的回到对应任务做完 |
| | 5.2 经验总结（原 8 的 lessons） | `lessons.json`、技能改动、台账、合成测试 | 报告不拒绝 lessons；`check_ledger.py` PASS；全部测试通过 |
| | 5.3 报告与打包（原 8 的报告、证据、打包） | 交付目录、`delivery-evidence.json`、`manifest.json` | `deliver.py` 各步为 DONE/PASS/FRESH，打包 PASS |

### 4.3 随之要改的

- **ASG 纲要“架构”**：现为“设计（第 0–3 步）/ 绘图（第 4–5 步）/ 验证（第 6–7 步）/ 交付（第 8 步）”，改为上面五个步骤；P1–P7 内容不变。
- **选择工作流**：“重画已有工程……再走第 4–8 步”改为“走步骤 ③–⑤”；“新增模块……第 2–8 步”改为“任务 1.4 起”；电气改版、审查意见处理同理。
- **编号引用**：SKILL.md、8 份 reference 与 `render_design_report.py` 等提示里约 30 处“第 N 步”改成新编号，如“第 2 步结束时”改为“任务 1.4 结束时”。
  `deliver.py` 的运行步骤名（准备、待办审计、出图、自动检查……）是脚本流程，不改。
- **结构测试**（同 SR 的 test_reading_path）：每个步骤 1–5 项编号任务，每个任务以“做完的标志”结尾，架构总表与正文编号一致。
